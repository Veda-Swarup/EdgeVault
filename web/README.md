# EdgeVault console

Plain HTML, CSS, and JavaScript connected to the existing Go API. The Go binary embeds the source assets, so normal use requires neither Node.js nor a frontend build.

## Run the complete local stack

Start Docker Desktop, then from the repository root:

```sh
make up
make run
```

Open http://localhost:8080. Create a volume, upload files, and open History to download earlier versions. Uploading an existing path prompts before creating a new version. Deleted files can be included using **Show deleted files**.

The browser acquires/releases a file lease for uploads and deletions. Uploads send the version observed in the dashboard using `If-Match`; stale writes surface the API error rather than silently overwriting another version. Upload leases expire after five minutes; uploads exceeding that duration can fail safely and should be retried. Multi-file uploads run sequentially and report partial completion. The progress bar counts completed files, not bytes transferred. Downloads are buffered in browser memory before saving, so very large downloads require sufficient memory.

## Optional frontend development with Vite

With the Go API running on port 8080:

```sh
cd web
npm ci
npm run dev
```

Open the local URL printed by Vite. Its development proxy forwards `/v1`, `/healthz`, `/readyz`, and `/metrics` to Go. Node.js runs development/build tools only; there is no Node backend.

```sh
npm run build
```

This validates and bundles the frontend into `web/dist`. The normal Go build deliberately embeds the original `index.html`, `style.css`, and `app.js` rather than this optional bundle. Rebuild Go after changing those assets. Vite builds require Node.js 20.19+ or 22.12+.

## Troubleshooting ports

Use port **8080** for the embedded Go dashboard. Port **5173** works with the API only when served by `npm run dev` with the configured Vite proxy and Go running on port 8080. A plain static server on 5173 returns 404 for `/v1/volumes`. The one-off preview on **5174** uses temporary in-memory file storage and is not part of the normal startup commands. See the [main README](../README.md#ports-and-troubleshooting) for the full troubleshooting guide.

## Features and measurements

- Volume selection and creation; remembered selection is stored locally in the browser.
- File search, drag-and-drop uploads, downloads, deletion, and retained version history.
- Current logical file bytes, tracked stored chunk bytes, chunk counts, and retained version counts from PostgreSQL.
- Latest 100 snapshots, standard or protected snapshot creation, and full-volume restore with typed volume-name confirmation.
- Per-volume ransomware alert state; uploads and deletions disabled while an alert is open.
- API/database readiness and process metrics, including cache counters and chunk reuse.

Current file bytes cover live files only. Stored bytes include tracked encrypted/compressed chunks for retained history and chunks awaiting garbage collection; they exclude snapshot objects, database storage, S3 object versions, and local cache space. These totals are **not** a deduplication savings calculation. Runtime chunk reuse is a process counter across all volumes since startup, not a volume-specific storage saving. The backend type is configured by the Go service; the UI does not assume AWS is deployed. Protected snapshot rows record that Object Lock was requested at creation, not the remaining retention period.

## API additions

- `GET /v1/volumes`: safe volume summaries (no wrapped encryption keys).
- `GET /v1/volumes/{volume}/dashboard`: volume policy/alert summary, files including tombstones, storage totals, and recent snapshots. File, storage, and snapshot reads use one consistent PostgreSQL transaction.

All writes reuse the existing API. The frontend introduces no authentication layer: the existing file/volume/snapshot API is unauthenticated. Keep this development console on a trusted local/private network until authentication and authorization are implemented. An admin retention token is never requested or stored by this UI.

## Source formatting

Frontend source uses two-space indentation, separate CSS declarations, and multiline HTML and JavaScript blocks. `app.js` and `style.css` include section comments to help locate related behavior. Go files use standard `gofmt` indentation. The settings in `.prettierrc.json` keep frontend formatting consistent in editors that support Prettier.

Edit the source files directly. Files under `dist/` are generated by Vite and may be compacted for delivery; rebuild them with `npm run build`.
